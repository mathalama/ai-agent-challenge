# Эталонная разметка

Каталог содержит эталонные разметки дефектов для расчёта метрик качества командой `rs eval`.

## Состав набора

- `requirements.golden.json` — эталон для документа организаторов `samples/requirements.md` («Уведомление о расходах по карте», 14 дефектов).
- `credit_application.md` и `credit_application.golden.json` — независимый синтетический документ другой финтех-области («Онлайн-заявка на потребительский кредит», 13 дефектов тех же классов с иными формулировками).

## Формат файла разметки (`*.golden.json`)

Каждый файл представляет собой JSON-объект со строгой схемой (неизвестные поля отклоняются):

```json
{
  "document": "../samples/requirements.md",
  "title": "Уведомление о расходах по карте",
  "defects": [
    {
      "id": "D-01",
      "requirement": "Ф-3, Ф-4",
      "criterion": "consistent",
      "acceptable_criteria": ["set_complete"],
      "severity": "critical",
      "lines": [39, 40],
      "description": "Краткое описание заложенного дефекта."
    }
  ]
}
```

### Поля верхнего уровня

- `document` (обязательно, строка) — путь к проверяемому документу. Относительные пути разрешаются относительно каталога файла разметки (с запасным поиском относительно текущей директории).
- `title` (необязательно, строка) — читаемое название документа для сводки `rs eval`.
- `defects` (обязательно, непустой массив) — список заложенных дефектов.

### Поля дефекта (`defects[]`)

- `id` (обязательно, уникальная строка) — идентификатор эталонного дефекта, например `D-01`.
- `requirement` (обязательно, строка) — идентификатор(ы) требования из документа (`Ф-3, Ф-4`) или название раздела/параметра (`Требования к тестированию`).
- `criterion` (обязательно, строка) — основной критерий ISO/IEC/IEEE 29148 / IEEE 830 в `snake_case`: `necessary`, `appropriate`, `unambiguous`, `complete`, `singular`, `feasible`, `verifiable`, `correct`, `conforming`, `set_complete`, `consistent`, `set_feasible`, `comprehensible`, `able_to_be_validated`, `ranked`, `modifiable`, `traceable`.
- `acceptable_criteria` (необязательно, массив критериев) — допустимые смежные критерии, если дефект может классифицироваться по ним.
- `severity` (обязательно, строка) — важность дефекта: `low`, `medium`, `high`, `critical`.
- `page` (необязательно для текстовых форматов; обязательно для PDF, целое число `>= 1`) — номер страницы документа, учитываемый при сопоставлении координат `SourceSpan`. Для DOCX поле `page` не задаётся.
- `lines` (обязательно, непустой массив целых чисел `>= 1`) — номера строк документа, к которым относится дефект. Для текстовых документов (`.md`, `.txt`) дополнительно проверяется, что номера не выходят за пределы файла. Для DOCX это порядковые номера блоков/строк, которые выдаёт парсер (как в отчёте `rs check`), а не номера строк в исходном XML-файле.
- `description` (обязательно, строка) — краткое описание дефекта на русском.

## Правила сопоставления и метрики

Для каждого файла `*.golden.json` команда `rs eval` запускает конвейер проверки (с включённым кэшем `.cache/llm/` по умолчанию) и выполняет взаимно-однозначное сопоставление подтверждённых находок (`verified == true`) с эталонными дефектами:

1. Совпадает критерий (`finding.criterion == defect.criterion` или входит в `defect.acceptable_criteria`).
2. Совпадает требование с учётом страницы (`span.page == defect.page`): либо идентификатор требования из `finding.scope` (`source_id` или `id`) перечислен в `defect.requirement`, либо диапазон строк требования / доказательств находки (`finding.evidence`) пересекается с `defect.lines` на той же странице.

Метрики выводятся отдельно для каждого документа:

- `Precision = TP / total_findings` (дубли и неподтверждённые находки снижают точность).
- `Recall = TP / total_defects`.
- Список пропущенных эталонных дефектов (`id`, требование, критерий, важность, страница/строки и описание).

## Запуск

```sh
# Оценка по всем файлам *.golden.json в eval/ (с кэшем)
rs eval --golden eval/

# Оценка одного эталона без обращения к Gemini (mock)
rs eval --golden eval/requirements.golden.json --provider mock
```
