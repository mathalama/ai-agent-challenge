# JSON-отчёт проверки требований

`rs check --format json` выдаёт отчёт по [JSON Schema Draft 2020-12](report.schema.json).

## Поля отчёта

| Поле | Содержимое |
| --- | --- |
| `schema_version` | Строка с версией контракта. Текущая версия — `"1"`. |
| `passport` | Название документа, дата прогона (`YYYY-MM-DD`), модель и версия агента. |
| `blocks` | Блоки разобранного документа в исходном порядке. |
| `requirements` | Выделенные требования с идентификаторами, текстом, цитатами и координатами. Для требований из таблиц `table.block_id` ссылается на `blocks[].id`. |
| `findings` | Находки с областью проверки, критерием, серьёзностью, доказательствами, источником и признаком `verified`. Для области `requirement` поле `scope.id` ссылается на требование. |
| `summary` | Число требований, находок и проверенных находок, идентификаторы критических находок. |
| `readiness` | `blocked` при подтверждённых находках средней или большей серьёзности. Если таких находок нет, `checks_incomplete` присваивается при неполной проверке, отсутствии выделенных требований или неподтверждённых находках высокой либо критической серьёзности. В остальных случаях — `ready`. |
| `incomplete_stages` | Идентификаторы стадий, которые выполнены частично или пропущены из-за лимита ответа модели. Поле опущено, если лимит не помешал проверке. |
| `questions` | Открытые уточняющие вопросы, варианты ответа, приоритет, доказательства и ссылки на находки или требования. |
| `finding_answers` | Сохранённые ответы по идентификаторам находок. Поле опущено, если ответов нет. |
| `requirement_answers` | Сохранённые ответы по идентификаторам требований. Поле опущено, если ответов нет. |
| `standalone_answers` | Ответы по идентификаторам текущих вопросов без связанных находок или требований. Поле опущено, если ответов нет. |
| `unmatched_answers` | Сохранённые ответы по идентификаторам вопросов, которые отсутствуют в текущем прогоне. Поле опущено, если таких ответов нет. |

У блока есть числовой `id` (нумерация с 1 в пределах документа), `kind` и
`location`. У `heading`, `paragraph`, `list_item` и `code` содержимое лежит в
`text`. Заголовок также содержит уровень `level`, а код — язык `language`
или `null`. У `table` текст представлен массивом строк `rows`, каждая строка
содержит массив ячеек. Если присутствует `row_lines`, её элементы по тем же
индексам задают номера строк таблицы в координатах документа.

Диапазон `location.start_line`–`location.end_line` включительный, нумерация
начинается с 1. Для Markdown и TXT это строки исходного файла, для DOCX —
строки разобранного текста. В PDF `location.page` — номер страницы с 1,
а строки отсчитываются заново на каждой странице. В остальных форматах
`page` равен `null`. Для подсветки выбирайте блоки с той же страницей и
пересекающимся диапазоном строк из `evidence[].location`. Точный фрагмент
внутри этих блоков можно найти по `evidence[].quote`. При поиске учитывайте
нормализацию пробелов и кавычек, а для PDF — переносы слов.

## Стадии конвейера

Индикатор прогресса использует идентификаторы в порядке выполнения.

1. `segment` — выделение требований.
2. `facts` — извлечение фактов.
3. `rules` — проверка формальными правилами.
4. `requirement_checks` — проверка отдельных требований.
5. `set_checks` — проверка набора требований.
6. `consistency` — проверка на противоречия.
7. `ambiguity` — поиск неоднозначностей.
8. `verify` — сверка доказательств с документом и объединение находок.
9. `clarify` — подготовка уточняющих вопросов.

CLI записывает стадии в `stages` отдельной трассы при использовании
`rs check --trace <путь>`. Запись содержит `stage`, `duration_ms` и
`succeeded`. При ошибке конвейер останавливается на текущей стадии.

## События прогресса

`rs check --events <путь>` пишет события в JSON Lines: одна строка — один объект, файл сбрасывается после каждого события и доступен во время прогона. Тип события лежит в поле `event`. SSE сессии передаёт эти же события во вложенном поле `progress`, а рассуждения — отдельным событием `reasoning`.

| `event` | Поля | Когда |
| --- | --- | --- |
| `run_started` | `document`, `model`, `stages` (идентификаторы по порядку) | Перед первой стадией |
| `stage_started` | `stage`, `index` (с единицы), `total` | Перед стадией |
| `stage_finished` | `stage`, `index`, `total`, `duration_ms`, `succeeded`, `llm_calls`, `cached_calls`, `input_tokens`, `output_tokens`, `requirements`, `findings`, `questions` | После стадии, в том числе при ошибке |
| `llm_retry` | `stage`, `reason` (`http`, `transport`, `invalid_response`), `status` (HTTP-код или `null`), `delay_ms` | Перед паузой повтора запроса к LLM |
| `llm_reasoning` | `stage`, `text` | Полный текст рассуждения после ответа или попадания в кэш при включённом сборе |
| `llm_reasoning_delta` | `stage`, `delta` | Фрагмент рассуждения из потока OpenAI-совместимого провайдера |
| `fact_batch_split` | Поле `source_ids` содержит ID требований или элементов контекста | После превышения лимита ответа, если пачка делится пополам |
| `fact_source_skipped` | Поля `source_id` и `location` указывают на источник | После превышения лимита ответа для одного источника. Прогон продолжается с неполной проверкой |
| `stage_output_limit` | `stage` | Лимит ответа прервал стадию, прогон продолжается |
| `clarify_batch_split` | `finding_ids` | Лимит ответа, пачка находок разделяется |
| `clarify_finding_skipped` | `finding_id` | Лимит ответа при уточнении одной находки, прогон продолжается |
| `run_finished` | `duration_ms`, `succeeded` | В конце прогона или после стадии с ошибкой |

`llm_calls` считает все попытки стадии, включая повторы и попадания в кэш. `requirements`, `findings` и `questions` — состояние прогона после стадии, а не прирост.

```json
{"event":"stage_finished","stage":"requirement_checks","index":4,"total":9,"duration_ms":38150,"succeeded":true,"llm_calls":1,"cached_calls":0,"input_tokens":7100,"output_tokens":1600,"requirements":20,"findings":12,"questions":0}
```

## HTTP-сессия

`rs serve` по умолчанию слушает `127.0.0.1:3000` и раздаёт `web/dist`. API предназначено для локального запуска.
Сессии хранятся в памяти и удаляются при перезапуске. Сервер освобождает сессии после часа простоя при следующем обращении к ним или создании новой сессии.

| Метод и путь | Тело и результат |
| --- | --- |
| `POST /api/sessions` | `201` с UUID в `id` и приветствием в `greeting` |
| `POST /api/sessions/{id}/document` | Один multipart-файл в поле `file` до 20 МиБ. `202` после принятия |
| `POST /api/sessions/{id}/messages` | JSON с полем `text` до 16 КиБ. `202` после принятия |
| `GET /api/sessions/{id}/events` | SSE с журналом событий. `Last-Event-ID` возобновляет чтение с последнего известного события |
| `GET /api/sessions/{id}/report?format=json` | Готовый отчёт. Поддерживается `format=md` |
| `GET /api/schema` | JSON Schema отчёта |

В SSE-событии `message` поле `data` содержит JSON с типом в поле `event`.
Переходы состояния приходят как `state_changed`. Прогресс приходит как `progress`, итог — как `report_ready`.
`reasoning` передаёт `stage`, `delta` и `complete`. Сообщения чата могут содержать проверенные `citations`.
Отдельное SSE-событие `done` отмечает завершение принятой операции. Следующий POST следует отправлять после `done`.
Занятая сессия и запрос отчёта до первой успешной проверки возвращают `409` сразу.
Событие `history_gap` отмечает, что часть истории уже вытеснена. При удалении сессии сервер посылает `expired` и закрывает поток. Последующие запросы возвращают `404`.

## Совместимость

Поле `schema_version` обязательно. Старые отчёты без этого поля не проходят
проверку по схеме. Клиенту следует предложить повторный прогон для старого
отчёта и обновление интерфейса для отчёта с неизвестной версией.

В пределах версии допустимо добавлять необязательные поля. Клиенту
следует игнорировать незнакомые поля. Удаление или переименование
полей, изменение их типов или смысла, а также расширение закрытого
перечисления требуют новой версии схемы. Порядок ключей объектов значения
не имеет. Идентификаторы связывают сущности внутри одного отчёта.

Тест сверяет контрольную сумму опубликованной схемы с закреплённой суммой
для её версии. Для несовместимого изменения добавьте новую версию и её
контрольную сумму в `crates/cli/tests/report_contract.rs`. Сумму текущей версии
обновляйте только после проверки совместимости изменения.

## Схема и примеры

[report.json](fixtures/report.json) — отчёт mock-провайдера для
`samples/requirements.md`.

Следующая команда перегенерирует схему из Rust-типов.

```sh
cargo run -p cli -- schema -o docs/api/report.schema.json
```

`cargo test -p cli --test report_contract` проверяет схему, валидирует
mock-фикстуру и сверяет её со свежим отчётом. При сравнении
игнорируются дата прогона и версия агента в паспорте. Следующая команда
обновляет mock-фикстуру.

```sh
cargo run -p cli -- check samples/requirements.md --provider mock --format json --no-cache -o docs/api/fixtures/report.json
```

Для живого прогона с ключом Gemini в окружении или в `.env` выполните
следующую команду.

```sh
cargo run -p cli -- check samples/requirements.md --provider gemini --format json --no-cache -o reports/report.gemini.json
```
