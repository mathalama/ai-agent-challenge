# Архитектурные решения

## 001. Rust workspace и локальный CLI

Один бинарь принимает пути исходного документа и отчёта. Парсинг, доступ к модели и проверка качества вынесены в отдельные библиотеки с однонаправленными зависимостями.

## 002. Типизированные данные на границе модели

Стадии описывают ожидаемый ответ Rust-типами. Из типов строится JSON Schema. Ответ проходит десериализацию, а подтверждение цитат и сводка выполняются кодом.

## 003. Mock для сквозного прогона

Mock возвращает заранее определённую форму ответа для каждой стадии модели. Для проверки передачи координат `segment` использует один блок из входного документа. Зарегистрированные детерминированные правила проверяют весь документ и могут выявить подтверждённые блокирующие дефекты. Для вердикта «Готово» нужен прогон с реальным провайдером.

## 004. Локальные результаты и версия сборки

Отчёт, опциональная трасса и кэш записываются локально. Версия в паспорте берётся из короткого хеша Git и точного тега, если он есть. При сборке без доступного коммита указывается `unknown`.

## 005. Вердикт готовности в отчёте

Код вычисляет вердикт после сверки цитат. Проверки полные, если штатный конвейер завершился с реальным провайдером, выделено хотя бы одно требование, цитаты всех выделенных требований подтверждены и стадия `rules` успешно выполнила все зарегистрированные правила, которых должно быть хотя бы одно. CLI проверяет отсутствие раздела тестирования, его пустоту и заглушки. Раздел узнаётся по ключевым словам в заголовке (тестирование, тест-кейсы, испытания, testing) или по короткому жирному абзацу с таким названием. Без заголовков границы раздела не определить, поэтому для таких документов, включая TXT, правило не применяется и без подтверждённых блокирующих находок вердикт — «Готовность не подтверждена».

- «Не готово», если подтверждена хотя бы одна находка средней, высокой или критической важности. Этот вердикт имеет приоритет при любой полноте проверок.
- «Готовность не подтверждена», если подтверждённых блокирующих находок нет, но проверки неполные или остались неподтверждённые находки высокой или критической важности.
- «Готово» в остальных случаях.

В итог Markdown попадают все подтверждённые находки от средней важности. Список отсортирован от критической важности к средней и по убыванию числа затронутых требований внутри каждой группы. Находка по отдельному требованию учитывает указанное требование. Для находки по набору считаются уникальные ID требований, диапазоны строк которых пересекаются с доказательствами на той же странице. При равных приоритетах сохраняется порядок отчёта. Каждая строка ссылается на подробности находки.

В сводку критичных дефектов (`summary.critical_findings` в JSON и строка критичных дефектов в разделе «5. Сводка» Markdown) попадают все находки с важностью `critical`, а также находки с важностью `high`, относящиеся к критериям `verifiable`, `consistent`, `complete` или `set_complete` (непроверяемые, противоречивые и неполные формулировки). JSON включает все такие находки, а Markdown считает и выводит ссылками только подтверждённые (`verified`). Вердикт готовности и раздел «6. Итог» это правило не меняет.

## 006. Детерминированные правила и словарь через `CheckRegistry`

Формальные проверки вынесены в `CheckRegistry` (`crates/review/src/rules.rs`, `vague.rs`) и выполняются в стадии `rules` без вызова LLM. Встроенные правила проверяют структурные и текстовые инварианты документа: раздел тестирования, критерии приёмки, версию и дату, чек-лист ревью, блок согласующих, пустые обязательные поля таблиц, несогласованные типы полей API и размытые формулировки по словарю `dictionaries/ru-vague-terms.txt` с поддержкой словоформ и контекстных исключений. Выполнение кодом делает эти проверки воспроизводимыми, бесплатными по токенам и независимыми от колебаний модели, включая прогоны с `--provider mock`.

## 007. Проверка непротиворечивости через извлечение фактов и решатель

Стадия `facts` (`crates/review/src/facts.rs`) извлекает из требований и контекста типизированные факты (`FactData`: единицы измерения, диапазоны, типы полей, HTTP-методы, намерения операций, коды ответов, периоды и политики), привязанные к подтверждённым цитатам. Стадия `consistency` (`crates/review/src/consistency.rs`) группирует факты по сущностям и сначала запускает детерминированный решатель для явных конфликтов (разные единицы без преобразования, расхождение типов полей, безопасный HTTP-метод для изменяющей операции, несоответствие кодов и результатов ответа, расхождение периодов приёмки). Модель вызывается дополнительно только для групп, затрагивающих несколько источников, чтобы находить семантические противоречия без квадратичного перебора всех пар требований.

## 008. Дедупликация находок

Перед формированием отчёта `dedup.rs` объединяет пересекающиеся находки от разных стадий и правил в пределах одного требования или набора (`merge_findings_in_context`) и сужает область `Scope::Set` до конкретного требования, если все доказательства относятся к нему одному. При слиянии сохраняются все критерии, детекторы и исходные идентификаторы, а приоритет отдаётся подтверждённой находке; при этом независимые детерминированные правила и находки с запасными цитатами по разным критериям не сливаются. Это уменьшает шум от повторов между правилами и LLM-стадиями без потери трассируемости источников.

## 009. Цикл уточняющих вопросов и файл `*.answers.json`

Стадия `clarify` (`crates/review/src/clarify.rs`) формирует вопросы только по подтверждённым находкам, привязывает их к проверенным цитатам и при превышении лимита ответа модели рекурсивно делит пачку находок пополам. Команда `rs ask` (`crates/cli/src/ask.rs`) позволяет интерактивно ответить на открытые вопросы и сохраняет ответы в файл `*.answers.json` рядом с отчётом (или документом в режиме чата). При повторном `rs check` ответы подхватываются через `Report::with_answers`, снимают соответствующие открытые вопросы и отображаются у связанных находок и требований в Markdown и JSON, не отменяя блокирующий вердикт до правки исходного документа.

## 010. Общее ядро сессии в `agent`, локальный сервер с SSE и вторичность `web`

Логика интерактивной сессии (загрузка документа, запуск проверки, команды чата, ответы на вопросы, экспорт отчёта и поток событий `AgentEvent`) сосредоточена в крейте `agent`, чтобы терминальный чат и веб-интерфейс работали одинаково без дублирования. Крейт `server` предоставляет локальный REST API, хранит сессии в памяти с таймаутом простоя, передаёт прогресс и рассуждения по SSE с поддержкой `Last-Event-ID` и раздаёт статику `web/dist`. Веб-интерфейс остаётся тонким клиентом поверх сервера и вторичен по отношению к CLI, который самодостаточен для автоматических прогонов и проверки в терминале.

## 011. Оценка качества по эталонам (`eval`)

Каталог `eval/` хранит файлы эталонной разметки `*.golden.json` с дефектами и обязательными уточняющими вопросами, а команда `rs eval` прогоняет агент по этим документам с кэшированием ответов модели. Модуль `crates/review/src/eval.rs` строит максимальное паросочетание между подтверждёнными находками и эталонными дефектами, вычисляя `recall`, `precision`, список пропусков и близких совпадений по другому критерию (`near_matches`), благодаря чему дубли находок не завышают `recall` и честно снижают `precision`. Для документов с секцией `questions` дополнительно вычисляются покрытие эталонных вопросов и число вопросов без привязки к цитатам (`ungrounded`).
