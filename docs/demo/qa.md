# Вопросы жюри и ответы

Ответы опираются на код и документы репозитория. Где нужен замер на реальной модели, стоит пометка «заполнить после прогона».

## Почему Rust

- Один бинарь `rs` без среды выполнения: CLI, веб-сервер и чат запускаются одной командой (`docs/decisions.md`, решение 001).
- Строгие типы на границе модели. Каждая стадия описывает ответ Rust-типом, из типа строится JSON Schema, ответ проходит десериализацию и проверку схемы (решение 002). Ответ, не совпавший с типом, повторяется один раз, затем стадия падает с понятной ошибкой.
- Вердикт и сверка цитат — обычный детерминированный код, его проще тестировать и воспроизводить.
- Минус: порог входа выше, чем у Python, и меньше готовых LLM-библиотек. Клиенты Gemini и OpenAI-совместимых API написаны в проекте (`crates/llm`).

## Как агент не галлюцинирует

Модель предлагает находки, а решает код:

1. Каждая находка несёт дословную цитату и координаты (страница, строки). Стадия `verify` сверяет цитату с текстом разобранных блоков по строкам и странице, нормализуя пробелы и кавычки. Находка без найденной цитаты получает `verified: false`.
2. Неподтверждённая находка высокой или критической важности не даёт вердикт «Готово»: статус становится «Готовность не подтверждена».
3. Вердикт («Не готово», «Готовность не подтверждена», «Готово») считает код по правилам из `docs/decisions.md`, решение 005. Модель его не выбирает.
4. Часть проверок — детерминированные правила без LLM: пустой раздел тестирования, не заполненные версия и дата, размытые слова по словарю, расхождение типов полей запроса и ответа.
5. Уточняющие вопросы создаются только по подтверждённым находкам и должны нести цитаты.

Честно о пределах: цитата подтверждает, что текст есть в документе, но не доказывает, что вывод модели верен. На эталоне precision 40,0 % (нижняя оценка, см. `eval/README.md`): часть находок вне эталона, и среди них бывают реальные замечания, а бывают лишние. Человек читает отчёт.

## Что будет на другом документе

В `eval/` лежит независимый синтетический документ `credit_application.md`: «Онлайн-заявка на потребительский кредит», другая область, другие формулировки, 13 заложенных дефектов тех же классов. Замер на `gemini-3.1-flash-lite` от 26.11.2026: найдено 12 из 13 (recall 92,3 %), precision 46,2 %. Для `requirements.golden.json` — 8 из 14 (57,1 %) и 33,3 %.

Оговорка: оба эталона писала команда проекта, а промпты правились по этим же документам. Это не независимая оценка на скрытой выборке. Проверить на новом документе можно командой `rs check <файл> --provider gemini`.

## Сколько стоит прогон

Цену модели мы не фиксируем: тарифы меняются, число зависит от модели и объёма документа. Считается по трассе:

```sh
rs check <документ> --provider gemini --trace reports/trace.json
```

В `reports/trace.json` в `llm_calls[]` для каждого вызова записаны `stage`, `model`, `usage.input_tokens`, `usage.output_tokens` и `cached`. Формула:

```text
стоимость = Σ по вызовам (cached = false) ( input_tokens × цена_входа + output_tokens × цена_выхода )
```

Цены за миллион токенов берутся из тарифа выбранной модели. Вызовы из кэша `.cache/llm/` стоят 0 и помечены `cached: true`.

Порядок величины для `samples/requirements.md` (198 строк, 22 требования):

- Число вызовов модели в одном прогоне — **12** по трассе mock-провайдера (triage 1, segment 1, facts 5, requirement_checks 2, set_checks 1, ambiguity 1, clarify 1). Mock повторяет структуру вызовов, но не поведение реальной модели. Допущение: у реальной модели число вызовов то же, плюс повторы при невалидном JSON или ошибках сети.
- Токены на реальной модели: **заполнить после прогона** (сложить `usage` из трассы). В mock-прогоне токены показаны только для стадии `clarify` (1 341 → 192), остальные ответы из кэша.
- Время: при темпе по умолчанию 5 запросов в минуту (интервал 12 секунд) 12 вызовов занимают чуть больше двух минут. Это нижняя оценка по интервалу, без времени ответа модели.

## Как работает бесплатная квота и лимит запросов

- Ключ создаётся в Google AI Studio. Реальные лимиты бесплатного уровня зависят от проекта и модели и меняются, поэтому актуальные значения смотрите в [Активных квотах AI Studio](https://aistudio.google.com/rate-limit). В репозитории числа квоты не хранятся.
- Локальный ограничитель `LLM_REQUESTS_PER_MINUTE` (по умолчанию 5) равномерно разносит запросы: интервал = 60 секунд / значение. Значение нужно сверить с квотой вашего проекта.
- При HTTP 429 агент ждёт задержку из ответа Gemini или 60 секунд, если её нет. Сетевые ошибки и HTTP 5xx повторяются до четырёх раз с паузами 5, 15, 30 и 60 секунд. Повторы идут через тот же ограничитель.
- Кэш `.cache/llm/` хранит ответы по SHA-256 запроса. Повтор того же прогона не тратит квоту. Для показа запускайте демо на заранее прогретом кэше.
- Другие модели: `--provider openai` подключает OpenAI-совместимые сервисы (OpenRouter, Groq, DeepSeek, локальный Ollama). Для OpenRouter доступен фильтр бесплатных моделей в настройках.

## Что с PDF и DOCX

- Markdown, текст (UTF-8), PDF и DOCX поддерживаются парсерами `crates/doc`.
- PDF проверен: `rs check samples/qr-payments.pdf --provider mock` разбирает документ. В `samples/pdf/` лежат тестовые PDF разной вёрстки (колонки, таблицы с объединёнными ячейками, альбомная ориентация, 30 страниц). Файл, который не является PDF, даёт понятную ошибку «Не удалось разобрать PDF».
- В PDF номера строк отсчитываются заново на каждой странице. Координаты находки содержат страницу, подсветка в интерфейсе учитывает её.
- DOCX: парсер зарегистрирован и покрыт тестами крейта `doc`, образца DOCX в `samples/` нет, на демо он не показывается. Номера строк DOCX — порядковые номера строк разобранного текста, а не строки XML.
- Размер загрузки в веб-чате ограничен 20 МБ.

## Чего агент не умеет

- Не читает сканы и изображения: распознавания текста (OCR) в проекте нет. Текст внутри диаграмм берётся, только если он есть в текстовом слое PDF. Схемы и картинки как таковые не анализируются.
- Не знает предметную область банка вне текста документа и коротких подсказок в промптах. Не проверяет, соответствует ли требование регламентам и законодательству.
- Находит не все дефекты. По эталонам: 20 из 27 заложенных (74,1 %). Precision — нижняя оценка 40,0 %: возможны лишние находки, поэтому отчёт предназначен для аналитика, а не заменяет его.
- Не исправляет документ. Предлагает формулировки исправлений в находках, но текст не меняет.
- Уточняющие вопросы: покрытие эталонных вопросов на реальной модели **заполнить после прогона** (`rs eval --golden eval/`, метрика из задачи #48). Автоматическое покрытие считает совпадение по строкам и требованиям, а не качество формулировки.
- Веб-сессии хранятся в памяти сервера. История завершённых проверок хранится в браузере.
- Режим mock возвращает заранее заданные ответы и не показатель качества. Вердикт «Готово» возможен только на реальном провайдере.
