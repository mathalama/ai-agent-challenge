# Сценарий демо (4–5 минут)

Основной документ — `samples/requirements.md`. Все команды и клики проверены на `--provider mock` в веб-чате и в терминале. На реальной модели сценарий тот же, отличаются тайминг первой стадии и состав находок. Что не проверено, помечено «не проверено».

## Что показываем

1. Загрузка документа и ход девяти стадий.
2. Вердикт «Не готово» и главные дефекты.
3. Дефект в тексте документа: подсветка и цитата со строкой.
4. Уточняющие вопросы и ответ на один из них.
5. Экспорт отчёта.

## Подготовка один раз

```sh
npm --prefix web ci
npm --prefix web run build
cargo build -p cli
```

Сервер раздаёт собранный `web/dist`, поэтому после правок интерфейса `npm --prefix web run build` нужно повторить.

## Вариант A. Реальная модель с кэшем

Нужны `GEMINI_API_KEY` в `.env` (образец — `.env.example`) и сеть. Модель по умолчанию — `gemini-3.1-flash-lite`.

```sh
cargo run -p cli -- serve --provider gemini
```

Откройте `http://127.0.0.1:3333`. Темп запросов по умолчанию — 5 в минуту (`LLM_REQUESTS_PER_MINUTE`), то есть один запрос каждые 12 секунд. Первый прогон `samples/requirements.md` занимает минуты. Поэтому:

1. **За день до показа** прогоните документ один раз по шагам сценария ниже. Ответы модели лягут в `.cache/llm/`.
2. На показе запускайте тот же сервер из той же папки репозитория. Повторный прогон возьмёт ответы из кэша, квота не тратится, стадии проходят за секунды. Кэш нужно сохранить: не удаляйте `.cache/` и не запускайте с `--no-cache`.
3. Ключ записи — SHA-256 сериализованного запроса. Если изменились файл, промпт или модель, кэш не сработает и пойдут живые запросы.

Не проверено: прогон на реальной модели (в среде подготовки сценария нет ключа). Владельцу ключа нужно сделать репетицию и записать фактические тайминги в таблицу ниже.

## Вариант B. Запасной, `--provider mock`

Ключ и сеть не нужны. Mock отвечает за доли секунды, поэтому ход стадий в чате мелькает. Чтобы показать стадии медленно, используйте деморежим (шаг B2).

### B1. Живой сервер на mock

```sh
cargo run -p cli -- serve --provider mock
```

Откройте `http://127.0.0.1:3333`.

### B2. Деморежим без сервера (показ стадий)

```sh
npm --prefix web run dev
```

Откройте адрес из вывода (`http://localhost:5173`, порт Vite выбирается свободный). Сервера на 3333 нет, поэтому интерфейс переходит в деморежим на готовом отчёте. Нажмите «Попробовать на примере». Длительность стадии задаётся параметром `?stageMs=<мс>`, по умолчанию около 2,6 с на стадию, например `http://localhost:5173/?stageMs=1200`. Отчёт в деморежиме взят из `web/public/mock/report.json` и содержит критические находки, которых нет в живом mock-прогоне.

## Ход демо (вариант A или B1)

| Время | Действие | Что говорим и что видно |
| --- | --- | --- |
| 0:00 | Открыть `http://127.0.0.1:3333`. | Пустая рабочая область «Проверьте требования». Агент проверяет документ по ISO/IEC/IEEE 29148 и IEEE 830. |
| 0:20 | Нажать «Прикрепить файл» и выбрать `samples/requirements.md` (или перетащить файл). | Сообщение «Документ «Уведомление о расходах по карте» загружен. Блоков — 80, строк — 198». |
| 0:35 | Нажать «Проверить». | В чате идёт блок «Проверяем»: девять стадий `segment → facts → rules → requirement_checks → set_checks → consistency → ambiguity → verify → clarify` с временем и токенами. Часть стадий — код без LLM (`rules`, `consistency`, `verify`). |
| 1:15 | Появляется карточка «Отчёт готов». | Вердикт «Не готово», 22 требования, 12 находок (на mock). Главные находки — ссылки под карточкой. Вердикт считает код по найденным находкам, не модель. |
| 1:30 | Нажать «Открыть отчёт ↗». | Вкладка «Сводка»: вердикт, счётчики по важности, «Цитаты подтверждены 100 %», блок «Почему такой вердикт». |
| 2:00 | В «Почему такой вердикт» нажать «Показать в документе» у находки. | Вкладка «Документ»: исходный текст, найденные места подсвечены цветом важности, у выбранной находки открыта карточка справа с цитатой и строкой. |
| 2:30 | Нажать на другую подсвеченную фразу в тексте (например, Ф-3 на строке 39). | Справа открывается карточка находки. Противоречие показывает две цитаты рядом. Кнопка «Найти в тексте» снова мигает местом. |
| 3:00 | Вкладка «Находки». | Фильтры по важности, критерию, стадии и области, счётчик «Показано X из Y». У каждой находки ссылка «Показать в документе». |
| 3:20 | В чате нажать «Уточняющие вопросы». | Три вопроса с вариантами ответа и обоснованием «почему спрашиваем». |
| 3:40 | Нажать вариант ответа на первый вопрос, например «По дате проведения покупки». | В чате появляется `/answer Q-… <вариант>` и «Ответ на Q-… принят». Ответ сохранён для повторной проверки. |
| 4:00 | Вкладка «Экспорт», кнопки «Скачать JSON» и «Скачать MD». | Отчёт для передачи дальше. |
| 4:15 | Заключение. | Метрики из `eval/README.md`, ограничения (слайды 5 и 9). |

Ответ на вопрос в терминале (по заданию — `rs ask`), если нужно показать CLI:

```sh
cargo run -p cli -- check samples/requirements.md -o reports/report.md --provider mock --trace reports/trace.json
cargo run -p cli -- ask samples/requirements.md -o reports/report.md --provider mock
```

`rs ask` показывает вопросы по одному. Введите `#1`, чтобы выбрать вариант, или свой текст. Enter пропускает вопрос. Ответы пишутся в `reports/report.answers.json`. Повторный `rs check` с тем же `-o` показывает ответ под связанными находками:

```sh
cargo run -p cli -- check samples/requirements.md -o reports/report.md --provider mock
```

`reports/` не коммитится. Экспорт для показа: `--format json` пишет `reports/report.json`.

## Что показать в отчёте терминала (запасной путь, 1 минута)

```sh
cargo run -p cli -- check samples/requirements.md -o reports/report.md --provider mock --trace reports/trace.json
```

Во время прогона в stderr идёт ход по стадиям: время, токены, число требований и находок. Откройте `reports/report.md`: раздел «Итог» начинается с вердикта «Не готово». `reports/trace.json` содержит `stages` (длительность стадий) и `llm_calls` (модель, токены, признак `cached`).

## Метрики для заключения

Берутся из `eval/README.md`, замер на `gemini-3.1-flash-lite` от 26.11.2026:

| Эталон | Recall | Precision |
| --- | ---: | ---: |
| `requirements.golden.json` | 57,1 % (8/14) | 33,3 % |
| `credit_application.golden.json` | 92,3 % (12/13) | 46,2 % |
| Всего | 74,1 % (20/27) | 40,0 % |

Precision — нижняя оценка, находки вне эталона снижают её, даже если описывают реальные дефекты. Покрытие уточняющих вопросов на реальной модели: **заполнить после прогона** `rs eval --golden eval/` (задача #48).

## Если что-то пошло не так

| Ситуация | Что делать |
| --- | --- |
| Нет сети или ключа | Перейти на вариант B1 (`serve --provider mock`). Скажите, что mock возвращает заранее заданные ответы моделей, а проверка правил, сверка цитат и вердикт — настоящий код. |
| Квота исчерпана или HTTP 429 | Агент ждёт задержку из ответа Gemini или 60 секунд и повторяет запрос (повторы видны в stderr сервера, в чате их нет). Не ждите: переключитесь на кэшированный прогон (вариант A после репетиции) или на B1. |
| Прогон идёт долго | Это темп 5 запросов в минуту. Покажите вместо ожидания деморежим B2 со `?stageMs=1200` и заранее открытую вкладку «Документ». |
| Сервер не стартует: порт занят | `cargo run -p cli -- serve --provider mock --listen 127.0.0.1:3399` и откройте этот адрес. |
| Пустая страница после `serve` | Не собран интерфейс: `npm --prefix web run build`. |
| Загрузка файла не сработала | Показать деморежим B2 или терминальный путь (`rs check`). |
| Не открывается браузер | Показать записанное видео (ссылка в README, раздел «Демо»). |

## Чеклист подготовки перед показом

- [ ] `git pull`, `cargo build -p cli`, `npm --prefix web ci && npm --prefix web run build` выполнены на показываемой машине.
- [ ] `cargo run -p cli -- serve --provider mock` открывает чат; прогон `samples/requirements.md` доходит до «Не готово».
- [ ] Вариант A: `.env` с ключом, прогон выполнен минимум один раз, `.cache/llm/` не пуст, повторный прогон проходит быстро.
- [ ] Окно браузера 1440×900 или шире: отчёт открывается рядом с чатом. В узком окне он открывается поверх.
- [ ] Вкладки «Документ», «Находки», «Вопросы» открыты один раз заранее: проверено, что нет ошибок.
- [ ] Запасное видео записано и лежит локально, ссылка в README.
- [ ] Слайды `docs/demo/slides.pdf` открыты, метрики сверены с `eval/README.md`.
- [ ] Закрыты уведомления, отключено автоблокирование экрана.
- [ ] Прогон по сценарию сделан дважды подряд без ошибок (не проверено: нужна репетиция человека).
